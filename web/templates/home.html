Four layers between the model and your clusters

Each one can refuse independently. A request has to satisfy all of them, and the two policy layers are tested against a shared fixture corpus to prove they agree.

LAYER 1

Static guardrails

Dangerous reads cannot be expressed: Secrets and non-OCM kinds are absent from the allow-list, so they are refused before any API call.

LAYER 2

Kyverno admission

An independent second opinion in dry-run. A parity contract asserts it reaches the same verdict as layer 1 on every fixture.

LAYER 3

Human approval

Writes are two-phase. An Ed25519 token, minted by a person out of band, binds the exact content hash and expires.

LAYER 4

Least-privilege RBAC

No Secret reads, no exec, no arbitrary delete — enforced by the hub itself, not by the server asking nicely.

Watch the same four gates take two requests. Only one of them reaches a cluster, and a person had to sign for it.

A write is two calls with a person between them

The server holds a public verifier key and nothing else. The signing key stays with the person, on their own terminal, and the token it produces is bound to one content hash, one operation, and an expiry.

Almost all of this surface is read

The whole Open Cluster Management API is safe to inspect, so most of the server is readable and free. Only two toolsets can change anything, and only through the gate.

Two records of every call, with different jobs

The audit log is a safety artifact: append-only, hash-chained, and the thing an incident report is written from. The spans are a debugging one, and nothing safety-related trusts them.
